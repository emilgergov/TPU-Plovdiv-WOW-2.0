# КТ134-Ж — интеграция чрез GitHub без повторна ръчна конфигурация на Cloudflare
Дата: 25.11.2026 г.
Статус: архитектурно решение; НЕ е продукционно внедряване.

## Потвърдено от наличния код
- `.github/workflows/deploy-cloudflare-ai-author-v27.yml` вече използва `CLOUDFLARE_API_TOKEN` от GitHub Secrets за автоматичен upload/activation на `tpu-plovdiv-ai-author-v27` и последващи проверки.
- `.github/workflows/kt133-approved-visuals-deploy.yml` публикува одобрените визуални промени през GitHub Actions.
- `.github/workflows/kt134-auto-unit-tests.yml` проверява само изолираната КТ134, без продукционен deploy.
- Наличието на YAML workflow НЕ доказва, че секретите са още валидни или имат права за друг Cloudflare Worker/D1/R2.
- Публичното GitHub хранилище НЕ съдържа гарантирано текущия частен изходен код на КТ125. Не трябва да се създава имитация на защитения Worker или да се включват истински лични данни, токени, cookies и оригинали на преписки.

## Избран път
1. Всички промени и регресионни тестове се изработват в `kt134-auto-mode-isolated`. Без сливане в `main` до приемане.
2. Запазва се действащата КТ133, достъпът по КТ125, UUID/EG/деловоден номер по КТ126, и одобрената Word бланка.
3. Създава се **отделен** интеграционен workflow със съществуващия GitHub Actions подход; той не трябва да се задейства от обикновен push в `main`, да публикува в production или да използва продукционни данни за автоматични тестове.
4. Преди deploy се удостоверява с read-only preflight, че текущите Cloudflare права/секрети позволяват работа с тестов Worker, тестова D1 и частен тестов R2. При липса на ресурс/право — fail closed, без опит за подмяна на production. Ако нужната инфраструктура не съществува, еднократно предоставяне на права или създаване на изолирани ресурси може да е необходимо; това не може да се замести само с GitHub Pages код.
5. Интегрира се реален КТ125 server-side код, не браузърна симулация: локална сесия, case.edit/case.confirm/document.generate, origin, revision lock, idempotency, журнал, оригинални документи, нормативен и ГИС MASTER, EG Автор/рецензент.
6. Само в тестовата база се прилага `KT134_TEST_DRAFT_SCHEMA.sql`. Word DOCX остава в частния R2; не се допуска публикуване на преписки или секрети в GitHub артефакти.
7. Провежда се пълен тест: единствен избор на автоматичен маршрут → без междинни въпроси → мотивирано предложение + реален Word проект → окончателно експертно одобрение. Проверяват се отказ, ръчен маршрут, същият UUID, ревизионни конфликти и регресии към КТ133.
8. Едва след изрична приемка се планира публикуване чрез GitHub Actions, с проверка и rollback.

## Граници на текущия резултат
Това е проверен технически маршрут за минимизиране на ръчната Cloudflare работа. Не твърдим, че новият КТ134 endpoint работи в реален Worker, че GitHub Secrets са проверени, или че D1/R2 тестова инфраструктура е създадена. Докато те не бъдат доказани, не е безопасно да се активира реален интеграционен deploy.

## Задължителни условия за чистене на R2
`kt134-orphan-reconciler.mjs` е само изолиран инструмент с `dryRun=true` по подразбиране. За реално изтриване трябва сървърно сериализиране спрямо конкурентни R2/D1 записи, отделно разрешение и тестове; двойна проверка на препратки не е достатъчна гаранция сама по себе си.
