# КТ134-Ж.1 — GitHub-first read-only проверка на Cloudflare
Дата: 25.11.2026 г.
Състояние: GitHub workflow е записан в изолирания клон; изпълнението и резултатът от Cloudflare **не са потвърдени**.

## Какво е добавено
- `.github/workflows/kt134-cloudflare-github-first-readonly.yml` — автоматичен push-trigger само при промяна на този workflow в `kt134-auto-mode-isolated` и опция за ръчно стартиране, ако GitHub го предлага.
- Проверява синтаксиса на отделните KT134 модули.
- Извършва само HTTPS GET за валидност на съществуващия GitHub Secret `CLOUDFLARE_API_TOKEN` и настройки на gateway Worker.
- Публикува само видове/брой на binding-и, никога стойности, секрети, изходен код или лични данни.
- Ако е зададена GitHub Repository Variable `KT134_TEST_WORKER_NAME`, проверява само наличието и видовете binding-и на отделния тестов Worker. Изрично отказва известните production имена.
- Не изпълнява PUT/POST/PATCH/DELETE към Cloudflare, не прави D1 миграции, не зарежда оригинали и не активира KT134 endpoint.

## Важна граница
Проверка на съществуващия API token и gateway settings **не доказва** право за deploy, D1 query, R2 write или възможност за използване на реалните частни KT125 източници. Това трябва да се удостовери на следващ етап в независима среда; при липса на тестова среда процесът спира без да се засяга КТ133.

## Следващ интеграционен праг
1. Да се потвърди действителното изпълнение на read-only workflow и само безопасните му резултати.
2. Да се установи конкретен защитен тестов Worker и отделни D1/R2 ресурси, без преизползване на реални преписки.
3. Да се свърже реалният KT125 сървърен код с KT134 маршрута в тестов Worker, при сървърна повторна проверка на самоличност, права и ревизия.
4. Да се тестват отказ, паралелна редакция, независим рецензент, мотивирана процедура, реален DOCX и крайно експертно одобрение.
5. След приемка — GitHub Actions внедряване с rollback и без регресия спрямо КТ133.
